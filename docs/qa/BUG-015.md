# BUG-015 — Re-saving a freshly-loaded (pre-rejoin) map drops the rebind tags (spec-compliant, documented consequence)

**Severity:** P3 (nice-to-have / spec-compliant edge case — does NOT break any
frozen AC or the headline flow. Logged so the team is aware of an
operationally confusing consequence of a deliberate frozen design rule.)
**Component:** Backend — `app/server.py` (POST `/api/saves`) + `app/saves.py`
(`save_bundle`), operating on `app/session.py` `Entity.owner_name`

## The behaviour (observed in the live restart smoke, AC3 check)
Scenario: GM loads a save and opens it (`use_map`) → the session's tokens are
rebuilt as GM-controlled with in-memory `owner_name` tags (Alice→"Alice",
Bob→"Bob", Goblin→null). If the GM then **re-saves this session before any
player re-joins**, the NEW save's bundle stores those tokens with
`owner_name: null` for all of them (verified: `{"Alice": null, "Bob": null,
"Goblin": null}`). The grid, cells, doors, safe, and all positions/kind/
team/color round-trip **byte-exactly** — only the *rebind identity tag* is
dropped for that secondary save.

Consequence: a player joining with the matching name against the **secondary
(pre-rejoin) save** will NOT be rebound (the tag is null) — they get a fresh
token instead. The GM's original save still rebinds correctly.

## Why it happens (and why it is arguably correct)
`POST /api/saves` computes each entity's `owner_name` from the LIVE owner
(`server.py:362-364`): the controlling player's name, or `null` when the
entity is GM-controlled (`owner is None` or a stale player id). After a load,
the tokens are GM-controlled (the rebind is pending, `owner = None`, only the
in-memory `Entity.owner_name` tag is set). So a re-save writes `null`.

This matches the spec EXACTLY as written:
* `docs/design/save-load.md` §4.3: *"at save time … if `entity.owner` is a
  player id of a player P … `owner_name = P.name`; otherwise
  (`owner is None` — GM-controlled) `owner_name = null`."*
* Codified by `tests/test_saves.py::test_owner_name_is_controlling_player_name`
  (GM-controlled → `None`) and `test_owner_name_null_when_player_id_stale`.

So the implementation and its tests are consistent and spec-correct. The
"in-memory tag survives `use_map`" (spec §6.1) is only true *until the next
save* overwrites it — the spec does not state the tag survives a re-save.

## Why it's low-impact
* The headline E8 scenario works: **save (while players connected) → restart →
  load → rejoin by name**. The saved tags are written while the players are
  connected (owner = a real player id), so they persist correctly.
* Re-save-after-players-rejoined also works (owner is set).
* The only case that drops tags is the narrower: load a save, then re-save
  *before* anyone re-joins. In that case the secondary save is still a
  fully-correct map snapshot; it just won't rebind on its own.

## Impact
* GMs who "load → (nobody's online yet) → Save current map → restart" and then
  expect the NEW save to rebind will be surprised: that save won't rebind.
* Nothing is lost; the GM can delete the ambiguous save or rely on the
  original.

## Suggested resolution (pick one)
1. **Document it** (no code change): add a note to `docs/design/save-load.md`
   §7.4/§6.1 and the GM rejoin note that a re-save of a not-yet-rejoined
   loaded map re-stores those tokens as GM-controlled (no rebind tag), so a
   later load of that specific save won't auto-rebind.
2. **Preserve the tag** (code change, small): when the session's tokens were
   just rebuilt from a loaded bundle and are still unclaimed, carry the
   in-memory `Entity.owner_name` through into the save's `owner_name` even
   though `owner is None`. This needs a deliberate design decision because it
   deliberately diverges from the current §4.3 "null for GM-controlled" rule
   (and would need a test to pin the new behaviour + a spec edit, since the
   existing test asserts the null behaviour).

Recommended: option 1 (document) — the current behaviour is spec-consistent;
option 2 is a genuine spec change and should be a deliberate follow-up.
