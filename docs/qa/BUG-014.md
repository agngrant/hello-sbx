# BUG-014 — Player "character has been restored" rejoin toast is dead code (never fires)

**Severity:** P2 (should-fix — non-blocking: the core R4 requirement is met and
independently verified live; this is a spec'd player-facing UX signal that
simply never fires, plus confusing dead code. The task pre-clears this as
"acceptable unless the owner's core requirement is undermined" — the core
reclaim flow is NOT undermined, so the feature sign-off stays PASS. Logged
for accuracy because the shipped block is unconditionally dead, and the fix
is one line.)
**Component:** Frontend — `app/static/app.js` (`onWelcome`)

## File:line
- `app/static/app.js:241` — `function onWelcome(msg)`
- `app/static/app.js:252` — `applyState(msg);  // welcome = state + "you"` (runs BEFORE the block below)
- `app/static/app.js:307` — `state.entities = msg.entities || [];  // [] for players`
- `app/static/app.js:308` — `state.youEntity = msg.you_entity || null;`
- `app/static/app.js:269-279` — the rejoin toast block (the dead code)

```js
// Rejoin by name (save-load spec §7.5, R4): ... client learns of it here via you.entity_id.
if (state.role === "player" && state.you && state.you.entity_id &&
    !state.youEntity) {                                   // ← ALWAYS FALSE for a real character
  const ent = state.entities.find((e) => e.id === state.you.entity_id);
  if (ent) {                                              // ← [].find() for a player
    toast(`Welcome back, ${state.name} — your character "${ent.name}" ` +
          `has been restored.`);
  }
}
```

## Why it's wrong
`onWelcome` calls `applyState(msg)` at line 252 **before** this block. For a
player who rebinds a saved character, the welcome carries
`you_entity: <Entity.to_dict()>` (set by `state_for`/`welcome_for`,
`app/session.py:417,460`), so after line 252:
* `state.youEntity` is **the rebound entity** (truthy), and
* `state.entities` is `[]` (the frozen wire sends `entities: []` to players —
  `app/session.py:416`).

Therefore the guard `!state.youEntity` is **never true** for a player who
actually has a character, and even if it were, `state.entities.find(...)`
searches an empty list. The `Welcome back … your character "…" has been
restored.` toast (spec §7.5, the R4 rejoin UX table row "Joins with a name
matching exactly one unclaimed entity → **plus toast**") can **never fire**.

Verified with the Node harness (a player welcome carrying
`you.entity_id:"e1"`, `you_entity:{id:"e1",name:"Alice",...}`, `entities:[]`):
`onWelcome` sets `state.youEntity.id == "e1"` and emits **only** the generic
`Welcome, Alice.` toast — no "has been restored" toast. The same shape is
what the server actually sends on a rebind (see `welcome_for`), so this is
not a harness artifact.

This does NOT affect the underlying rebind: `you.entity_id` /
`you_entity` are correct, the "YOU" ring renders from `you_entity`, and the
player reclaims the character at its saved position — all verified live
(rejoin-by-name smoke, AC4). It is purely the *confirming toast* that is
dead.

## Repro steps (real server, restart scenario)
1. GM saves a map where player "Alice" owns a token; kill + restart the server.
2. GM loads the save and opens it (`use_map`).
3. A new socket joins as "Alice".
4. Expected (spec §7.5): the player sees `Welcome back, Alice — your
   character "Alice" has been restored.`
5. Actual: the player sees only the generic `Welcome, Alice.` — the rebind
   toast never appears. (The rebind itself works: Alice is on her saved
   token with the blue YOU ring.)

## Expected vs actual
- **Expected:** on a name-match rebind, the player is told their character
  was restored (the one line the GM rejoin note already covers for the GM).
- **Actual:** no such toast; the code path is unreachable.

## Proposed fix
Use `state.youEntity.name` (populated by `applyState` from the welcome's
`you_entity`, which carries `name` via `Entity.to_dict`). Detect the rebind
by comparing the welcome's roster: a rebound character was not a freshly
spawned one. Simplest correct form — toast when the player is bound to an
entity whose `name` came from the saved roster. Since the frozen wire does
not tag "was a save rebind" (no new field allowed), a pragmatic trigger is:
the player joined, is bound, and the entity name matches the player name is
*not* sufficient to distinguish fresh-spawn. A clean, wire-safe option is to
drop the `!state.youEntity` guard and key off the entity being present while
the player just joined; but to avoid a false-positive on ordinary fresh
joins, the server would need to signal it. Given the frozen-wire constraint,
the minimal honest fix is either (a) remove the dead block, or (b) have the
GM's rejoin note be the single source of truth and drop the player toast
claim from the spec. Recommended: **(b)** — remove lines 269-279 and update
`docs/design/save-load.md` §7.5 to note the player gets only the standard
welcome (the GM is told via the rejoin note), OR add a one-byte additive
`rebound` flag to the player's `you_entity` (additive, ignored by old
clients) to drive the toast. Any of these is a one-line change.
