# BUG-008 — Reconnect/open-map race: a closed socket's `onclose` schedules a stray reconnect

**Severity:** P3 (minor/cosmetic — resource leak + transient "double socket"; not user-visible if fix for BUG-002 also lands)
**Component:** Frontend — `app/static/app.js` WS lifecycle

## File:line
- `app/static/app.js:135` — `ws.onclose = () => { if (state.joined) scheduleReconnect(); }`
- `app/static/app.js:142-150` — `scheduleReconnect()` (sets a `setTimeout` that calls `connectWs()`)
- `app/static/app.js:1097-1101` — `openUploadedMap` does `if (ws) ws.close(); connectWs();` after changing `wsSession`

## Why it's wrong
When `openUploadedMap` calls `ws.close()`, the old socket's `onclose` fires **asynchronously**. Because `state.joined` is still true, `onclose` calls `scheduleReconnect()`, arming a `setTimeout` that will call `connectWs()` in ~1 s — even though the app *already* opened a fresh socket to the new session via the explicit `connectWs()` in `openUploadedMap`. So the GM briefly ends up with **two open sockets to the same session** (the intended new one + the stray reconnect one). Both re-join by name, so functionally the session state is correct (re-attach is idempotent by name), but:
- two sockets to the same server session are held simultaneously (the extra one is orphaned from `state` — the module-level `ws` points at the newest, the older one has no JS reference and is never explicitly closed → a leaked browser WebSocket + a leaked server handler thread until it times out).
- `reconnectDelay`/`reconnectTimer` bookkeeping can desync.

## Repro steps
1. (After BUG-002 fix, or as-is) GM in session `default`, joined.
2. GM opens a new map and clicks "Open map in session".
3. Watch the browser Network → WS: two `ws://…/ws?session=…` handshakes open close together; one is never closed by the client.

## Expected vs actual
- **Expected:** closing the old socket for a deliberate session switch does not schedule a reconnect; only a single live socket exists at any time.
- **Actual:** `onclose` treats the deliberate close as an unexpected drop and schedules a stray reconnect, producing a transient second (leaked) socket.

## Proposed fix
Guard the intentional close. Add a flag, e.g. `let _intentionalClose = false;`; set it `true` in `openUploadedMap` right before `ws.close()`, and in `onclose` do `if (_intentionalClose) { _intentionalClose = false; return; }` before `scheduleReconnect()`. (A general "only one `connectWs()` in flight / clear any pending `reconnectTimer` in `connectWs()`" also hardens this.)
