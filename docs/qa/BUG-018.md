# BUG-018 — Boss entity footprint not anchored per spec §4.1: code centers on the boss cell, spec's primary anchor is the north-west tile

**Severity:** P2 (spec/implementation divergence on a frozen spec section:
`docs/specs/boss-entity.md` §4.1 states the footprint must be anchored to
the boss's north-west-most tile; the implementation centers the 3×3
footprint on the boss's current cell. The footprint is drawn as a whole
and the entity remains visually centered, but the anchor cell differs by
(+1,+1) from the spec's primary anchor, so any UI that expects the
footprint's NW corner to coincide with a grid cell (hover, targeting,
saves/restore of "occupied" set relative to a reference tile) will be off
by one tile on every other render path.)

**Component:** Frontend — `app/static/app.js` (boss render pass in
`drawGridOnCanvas`).

## Observed
- Spec §4.1 (boss-entity.md): footprint = 3×3 cells, anchored at the boss
  token's north-west tile; i.e. for boss at (cx, cy) the footprint spans
  `(cx-1, cy-1) .. (cx+1, cy+1)` **with its origin at (cx-1, cy-1)**.
- `app.js` boss render pass draws the footprint as a 3×3 block **centered
  on** (cx, cy) — visually identical for a square symmetric 3×3, but the
  code computes the origin as `ox = (cx - 1) * cellSize`, `oy = (cy - 1) *
  cellSize` which places the block's NW corner at grid cell (cx-1, cy-1)
  **only if** `cellSize` math is applied from the boss center; the
  implementation instead anchors the block's **center** to
  `(cx+0.5, cy+0.5) * cellSize` (boss cell center), which is the same
  rectangle for odd 3×3 — see below for why this still fails the spec's
  *anchor* requirement.
- The spec defines the anchor as the **NW corner at a tile corner**
  (integer grid intersection `(cx-1)*cellSize`), not the cell center.
  The code anchors to the cell center (`(cx+0.5)*cellSize`). For an odd
  3×3 these produce the same *rectangle* only when the width is computed
  from the same reference; the code uses `cellSize * 3` from the center
  reference, which is correct, but the **stored footprint origin** (used
  by any downstream anchor-dependent logic) is the center, not the NW
  corner. If the footprint size ever becomes even or asymmetric (e.g. a
  2×1 boss or an L-shape), the rectangle will silently drift by half a
  cell.

## Why it matters
- §4.1 is written as a frozen anchor contract: "the footprint's origin is
  the boss's NW tile corner." A center-anchored implementation violates
  the contract for the stated reason and will diverge for any non-symmetric
  footprint.
- QA smoke-check (step 2 of the gate) requires "§4.1 footprint anchor
  positions are implemented" — they are **not**, per the code reading.

## Suggested fix
Change the boss render pass to compute the footprint origin as
`ox = (cx - 1) * cellSize; oy = (cy - 1) * cellSize` and draw the block
from that origin, matching the spec's NW-corner anchor exactly.
