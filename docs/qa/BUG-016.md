# BUG-016 — Save-delete modal: edge cases E1 (idempotent same-id re-entry) and E11 (unknown-id membership guard) are code-correct but lack dedicated harness tests

**Severity:** P3 (test-coverage gap — NOT a product defect. The code behaves
exactly as specified in both cases; this is logged per house convention so the
team can add the missing guards and so future regressions in these paths are
caught.)
**Component:** Tests — `tests/test_frontend.py::TestSavesDelete` (frontend
spec `docs/design/save-load-delete-modal.md` §9 edge cases E1 and E11).
**Verified by:** QA independent suite re-run + direct Node harness probe
(`scripts/qa_modal_e11_probe.js`) on branch `feat/save-load`.

**Status:** ✅ **CLOSED** — both edge cases now have dedicated harness tests
(`test_e1_same_id_reentry_idempotent`, `test_e11_unknown_id_no_modal` in
`TestSavesDelete`). QA re-verified with independent re-runs: **793 pytest /
233 frontend**, 0 failed (closure note below; addendum in
`docs/qa/qa-signoff-delete-modal.md`).

## The finding
The spec (§9) enumerates 12 edge cases (E1–E12). Every one is exercised by a
dedicated harness test **except two**:

* **E1 — Double-click the row's Delete / programmatic same-id re-entry.**
  The spec says: *"Programmatic double-call of `confirmDeleteSave('act-1')` is
  idempotent: same flag, same single modal, no duplication, no request."*
  No test in `TestSavesDelete` (or elsewhere) calls `confirmDeleteSave` twice
  with the same id. (The in-browser half — a second click landing on the
  backdrop — is inherently untestable in the harness and is covered by the
  `ev.target` check in AC7a; but the *programmatic* double-call the spec
  explicitly names is not tested.)
* **E11 — Unknown id reaches `confirmDeleteSave`.** The spec says: *"no modal
  opens; error toast `save not found: <id>`; no request."* No test calls
  `confirmDeleteSave` with an id that is **not** in `state.saves`.

QA reviewed every `confirmDeleteSave(` call site in `tests/test_frontend.py`:
all use the fixture ids `act-1` / `old-1` / `bad-1` (all present in
`state.saves`), and none is called twice for the same id.

## Why it is low-impact (code is correct)
QA probed both paths directly against the **real** `app/static/app.js` under
Node (`scripts/qa_modal_e11_probe.js`). Both behave exactly as specified:

* **E11** (`confirmDeleteSave("does-not-exist")`): `state.confirmingSaveId`
  stays `null`, the modal stays `hidden=true`, the error toast
  `save not found: does-not-exist` fires, and **no** fetch/DELETE is issued.
* **E1** (`confirmDeleteSave("act-1")` called twice): the single modal opens
  once (exactly one `#save-delete-modal` instance), `confirmingSaveId ===
  "act-1"`, the body names `Delete "Act Three"?`, **no** fetch is issued, and
  no duplicate/toast.

So the shipped behavior is correct; only the *regression guard* is missing.

## Impact
A future refactor of `confirmDeleteSave`'s membership guard or re-entry
handling could silently break E1/E11 with no test to catch it. Low risk today
(the guard is a 4-line membership `find` + early return), but these are the
"never delete without the GM passing through the modal" invariants, which
merit an explicit guard.

## Suggested resolution (add two tests to `TestSavesDelete`, mirror AC6/AC13 style)
* `test_e11_unknown_id_no_modal`: GM + `state.saves=[act-1]`;
  `confirmDeleteSave('ghost-99')`; assert `confirmingSaveId===null`,
  `saveDeleteModal.hidden===true`, a toast `save not found: ghost-99`, and
  `api._fetch.sent.length===0`.
* `test_e1_same_id_reentry_idempotent`: GM + `state.saves=[act-1]`;
  `confirmDeleteSave('act-1')` **twice**; assert `confirmingSaveId==='act-1'`,
  exactly one `#save-delete-modal`, body names `Act Three`, and no fetch
  recorded.

Both are trivially implementable with the existing harness (no new harness
support needed). No code change is required.

## Closure (QA, branch `feat/save-load`)
**Closed by:** the two proposed tests, added by frontend_engineer as a
**test-only** change — `tests/test_frontend.py` is the *only* file touched
since QA's smoke run (product `app/static/*` + `app/*.py` untouched; the
`scripts/qa_modal_*` probes and this file + the sign-off are QA artifacts).

**New tests (both in `TestSavesDelete`, now 25 tests total):**
* `test_e1_same_id_reentry_idempotent` — GM + `state.saves=[act-1]`,
  `confirmDeleteSave('act-1')` twice; asserts modal open, `confirmingSaveId == 'act-1'`,
  the single static `#save-delete-modal` shell, body built exactly once
  (name/meta/note, `Delete "Act Three"?` name line not duplicated), row in
  normal shape, **`api._fetch.sent.length===0`** (zero requests), and no
  `save not found` toast.
* `test_e11_unknown_id_no_modal` — GM + `state.saves=[act-1]`,
  `confirmDeleteSave('ghost-99')`; asserts `confirmingSaveId === null`, modal
  `hidden === true`, **`api._fetch.sent.length === 0`** (zero DELETEs), the
  dialog body never filled, and a `save not found: ghost-99` toast.

Both assert exactly what spec §9 E1/E11 require and mirror the AC6/AC13
style. QA re-ran independently: `tests/test_frontend.py` Node harness **233
passed** (25 in `TestSavesDelete`); `.venv/bin/python -m pytest tests/ -q`
**793 passed, 0 failed** (both new tests verified passing in isolation).
