# BUG-005 — Per-client reply is sent without the send-lock → frame-interleaving race

**Severity:** P2 (moderate — intermittent WS frame corruption under concurrency)
**Component:** Backend — `app/ws.py` `ws_serve` ↔ `app/session.py` `_broadcast`

## File:line
- `app/ws.py:394` — `send_json(sock, reply)` (sent **without** the per-connection send lock)
- `app/session.py:309` — `_broadcast` sends on each socket **under** its per-connection lock
- `app/session.py:457` — a failed `move` returns `{"type":"error","message":NO_ROUTE}` (sent via the unlocked `ws_serve` path)

## Why it's wrong
`ws_serve` (one thread per connection) runs `reply = on_message(sock, msg)` and then, if a reply dict is returned, calls `send_json(sock, reply)` **directly** — bypassing the per-connection send lock that `_broadcast` uses.

A reply is returned (→ sent on that path) for: unknown type, `join first`, `not allowed`, `session full`, and a **no-route move rejection** (`app/session.py:457`). Meanwhile another client's successful move/paint triggers `_broadcast`, which sends to *the same* socket **under** its send lock. Two threads can therefore call `sock.sendall(...)` on the same TCP socket concurrently — one locked, one not. `sendall` is not atomic across threads, so the two frames can **interleave bytes**, producing a malformed/corrupted WebSocket frame on that client (garbage JSON or a framing error), which can desync or kill the connection.

Trigger requires two concurrent operations targeting the same client, e.g. a player's move no-routes (unlocked reply) at the same instant a GM/paint broadcasts to them. Plausible with 1 GM + 6 players active (the "4+ concurrent connections" scenario).

## Repro steps (probabilistic)
1. Start the server. GM + a few players on one session.
2. Have a player repeatedly attempt wall-blocked moves (→ `no route` reply via the unlocked path) while the GM simultaneously moves entities / paints (→ broadcasts to the same player via the locked path).
3. Under load the player's socket intermittently receives a corrupted frame (JSON parse error / WS framing error in the browser console; the client then drops to reconnect).

## Expected vs actual
- **Expected:** every write to a given socket is serialized by that socket's send lock; frames never interleave.
- **Actual:** the `ws_serve` reply path writes to the socket without the lock, so it can interleave with a concurrent broadcast to the same socket.

## Proposed fix
Either (a) route the reply through the same per-connection send lock, or (b) simplest: have `session.handle_message` perform the send itself under the connection's lock (it already has `_send_lock_for(sock)`) and have `ws_serve` **not** send the reply. Minimal change: in `ws_serve`, acquire the connection's send lock around `send_json(sock, reply)` — i.e. give `on_message` access to the lock or expose `send_to_client(sock, obj)` in the session that takes the per-socket lock, and call that instead of a bare `send_json`.
