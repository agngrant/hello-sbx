# BUG-002 — Opening an uploaded map switches sessions, stranding the players

**Severity:** P1 (major — breaks the combined hard-requirements #1 + #8 flow)
**Component:** Frontend `app/static/app.js` ↔ server session routing `app/main.py`

## File:line
- `app/static/app.js:1089` — `openUploadedMap()`
- `app/static/app.js:1097` — `if (target !== wsSession) { wsSession = target; ... connectWs(); }`
- `app/static/app.js:107` — `let wsSession = "default";` (hardcoded; there is **no** session/room picker in the lobby)
- `app/main.py:92` — `get_session(session_id)` creates a fresh `GameSession` per session id

## Repro steps
1. Start the server. GM opens the page and joins session `default` (sample map).
2. One or more players open the page and join as players (they connect to `/ws?session=default`, because `wsSession` is hardcoded).
3. GM clicks **New map…**, uploads `crypt.png` → server registers a new map with id `crypt`.
4. GM clicks **Open map in session**. `openUploadedMap` sets `wsSession="crypt"` and reconnects the GM to `/ws?session=crypt`, then re-joins.

## Expected vs actual
- **Expected (wireframes §7 note):** "players who connect during the preview simply see it live" — i.e. the *same* session continues, now playing the new map, and everyone stays together.
- **Actual:** The GM moves to a *different* session (`crypt`). The players remain in session `default` (they have no way to learn or select the new session id). Result: the GM plays `crypt`, the players play the stale `default` (sample) map, and the GM's old `Player` slot in `default` is left dangling. The "1 GM + up to 6 players in **one** session" guarantee (hard req #1) is violated the moment a custom map is used (hard req #8). The flagship "GM uploads a map and 6 players play on it" scenario is unusable.

**Note (aggravating):** the switch also triggers a reconnect race — `ws.close()` fires the old socket's `onclose`, which calls `scheduleReconnect()` while `connectWs()` is already opening a second socket to the new session, so the GM briefly holds two sockets to the same session (one is orphaned). Harmless functionally (re-attach is idempotent by name) but a leak.

## Proposed fix
Do **not** change the session id when opening a map. Keep the session and swap its grid to the newly uploaded one, e.g.:
- Add a server concept of "set the current session's map to `<map_id>`" (or have the GM's upload replace the live session grid), so every connected client's next `state` broadcast carries the new map — no reconnect, no stranded players.
- Alternatively, give the lobby a **room/session code** field so all clients join the *same* explicit session id (and have the GM share that code). Then `openUploadedMap` just updates `state.mapName` and waits for the next `state` (no `wsSession` switch).

Either way, the invariant to restore is: *after "Open map in session", the GM and all players are in one session playing the new map.*
